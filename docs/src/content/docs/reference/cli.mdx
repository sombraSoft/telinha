## telinha run

<HelpText locale="en" topic="helpRun" />

`run` is the default: `telinha` alone does the same. It takes only the global
flags. On a terminal with no `telinha.env` yet it offers to start the setup
instead, and after a double-click it waits for Enter so the window does not
vanish. Only one `run` per home directory: a second one (a console run while
the service is up) leaves the first alone and exits 1 with
`Telinha is already running (pid N)`.

## telinha setup

<HelpText locale="en" topic="helpSetup" />

<FlagTable locale="en" command="setup" />

On a terminal, setup opens full-screen screens: the steps down the left (Where,
Address, Discord, Ports, Updates, Review, Install), one question at a time as a
card with a hint, then the Review and a live Install list; [Keys](#keys) lists
the keys. `--yes` counts every question that already has an answer as answered,
whether it came from a flag, from the existing `telinha.env` or from the
machine's own suggestion, so the screens open on the first one that has none
(often the bot token) or on the Review when every question has one; nothing is
written before you apply there. A rule that a flag breaks (for example
`--host home --public-url https://x.example` without `--advanced`) shows as a
notice on the first card, and that flag is not used as a default.

With `--non-interactive` (implied without a terminal) nothing opens: every
answer comes from flags, then the environment (any `telinha.env` key), then the
existing file, and the run prints plain lines. A flag that breaks a rule, or a
missing answer, exits 2 naming the flag or variable. Required:
`--public-url` (or `--duckdns-domain`), the bot token, the client secret,
`--guild`, `--role`, `--channels`, plus the tunnel or DuckDNS token in those
modes.

`--host home|vps` (or `HOSTING`) picks the defaults the setup screens
would; without it the existing file decides, else a guess from the machine
that is `home` unless it clearly is a VPS. At home, `--duckdns-domain` means
HTTPS on `--https-port` (8443) with a certificate through DuckDNS, and
`--ingress tunnel` a Cloudflare Tunnel; Telinha never counts on ports 80 and
443 there. A home install:

```
telinha setup --non-interactive --host home --duckdns-domain my-group \
  --duckdns-token-file ./duckdns-token \
  --guild <id> --role <id> --channels <id>,<id> \
  --discord-token-file ./discord-token --client-secret-file - < ./client-secret
```

A script for a VPS passes `--host vps` instead, and there `--public-url` or
`--duckdns-domain` is served directly on 443.

## telinha doctor

<HelpText locale="en" topic="helpDoctor" />

<FlagTable locale="en" command="doctor" />

Exit 1 when a check or the phone test failed. On a terminal doctor is an
interactive checklist ([Keys](#keys)); without one, or with `--json`, it prints
plain lines (see [Doctor and troubleshooting](/telinha/guides/doctor/)). The
checks are listed in [Doctor checks](/telinha/reference/doctor-checks/).

## telinha update

<HelpText locale="en" topic="helpUpdate" />

<FlagTable locale="en" command="update" />

With the service running the request goes to it; with the service stopped the
new executable is staged and the next start uses it.

```
telinha update --check     # current version, newest stable (or the pin), staged / failed / pending
telinha update             # with the service running: check and install now unless rooms are open
telinha update --now       # install even with rooms open; also retries a failed tag
```

## telinha service

<HelpText locale="en" topic="helpService" />

<FlagTable locale="en" command="service" actions />

<FlagTable locale="en" command="service" />

`--user` differs by platform: on Linux it is a switch that installs a user
unit (`~/.config/systemd/user/telinha.service`, `systemctl --user`) instead of
the system one; on Windows it takes the account the Task Scheduler task runs
as, which the elevated install passes along with `--sid`.

## Keys

The setup screens and the doctor checklist read these keys. The key help in the
last row of the terminal always shows the ones that work on the screen you are
on.

**Setup**

| Key | What it does |
| --- | --- |
| `↑` `↓` (or `k` `j`) | Move between options |
| `1`-`9` | Pick the option with that number |
| `Enter` | Choose the option, or confirm a typed answer |
| `Space` | Mark or unmark an option in a multiple choice (the channels) |
| `a` | Mark all, or none, in a multiple choice |
| `Esc` or `←` | Back to the previous question; the answers stay. From the step list, back to the card. Off while the install runs |
| `Tab` | Focus the step list; there `↑` `↓` move, `Enter` or `→` jumps to a step already answered, `Esc` returns. Under 80 columns the list is hidden and `Tab` shows it in place of the card |
| `Ctrl+U` | Clear a text field |
| Paste | Into a text or secret field, with the terminal's paste shortcut (`Ctrl+V`, often `Ctrl+Shift+V`) |
| `Ctrl+R` | Show or hide a secret you typed or pasted |
| `PgUp` `PgDn` | Scroll a long Review |
| `Ctrl+C` | Quit setup. During the install, press it twice: stopping half way can leave a half install |

A secret field shows dots, never the text, and says only how many characters
were typed or that the text was pasted. On the Review a secret is `set`, `kept`
or `generated`.

**Doctor**

| Key | What it does |
| --- | --- |
| `↑` `↓` (or `k` `j`) | Move between rows |
| `Enter`, `Space` or `→` | Open or close a row: its details and, when it is not ok, the fix |
| `r` | Run every check again |
| `p` | Start a new phone test |
| `s` | Stop waiting for the phone |
| `q` or `Esc` | Quit (inside the setup, back to its last card). `Ctrl+C` quits the whole command (exit code 130 for `telinha doctor`) |

## Colours

The screens use the terminal's own foreground and background, and the Telinha
accent colour for the focus. They find out whether the terminal is light or
dark by asking it, then from `COLORFGBG`, else assume dark; some terminals, the
older Windows console host among them, do not answer, so set `TELINHA_THEME`
to `light` or `dark` to force one. With `NO_COLOR` set, every colour becomes
the terminal's own.

```
TELINHA_THEME=light telinha setup     # or dark
NO_COLOR=1 telinha doctor
```

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | ok |
| `1` | error; also `doctor` with a failed check, and `service status` when the service is not installed or not running |
| `2` | usage: a bad flag, an unknown command, a missing non-interactive answer |
| `3` | restart requested: `run` asking the service loop to start it again, after an update |

## Secrets

Secrets never go on the command line: the process list and the shell history
show it. They come from the environment under their `telinha.env` name, or
from a file given to the matching `-file` flag; `-` reads stdin, one secret
per run. The flags `--discord-token`, `--client-secret`, `--tunnel-token` and
`--duckdns-token` are refused with a usage error saying so.

| Secret | Environment | File |
| --- | --- | --- |
| Bot token | `DISCORD_TOKEN` | `--discord-token-file PATH` |
| Client secret | `DISCORD_CLIENT_SECRET` | `--client-secret-file PATH` |
| Tunnel token | `TUNNEL_TOKEN` | `--tunnel-token-file PATH` |
| DuckDNS token | `DUCKDNS_TOKEN` | `--duckdns-token-file PATH` |

## Version and help

`telinha --version` prints one line, for example
`telinha 0.7.0 (abc1234, bun 1.4.2, windows-x64)`. `telinha help [command]`
prints the texts above in the language picked by `--lang`, else `LOCALE`,
else the system's.
