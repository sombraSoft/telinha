Uma VPS tem IPv4 público próprio, então não há roteador para configurar e o
CGNAT não atrapalha. No lugar disso, você libera as portas no firewall do
provedor. Sem domínio, o sslip.io dá ao servidor um nome HTTPS feito a partir
do IP.

## Antes de começar

- Uma VPS com uma imagem atual de 64 bits do Ubuntu LTS ou do Debian (Fedora
  e outras distribuições com systemd também servem), x64 ou arm64, com IPv4
  público e um login como root ou como um usuário com `sudo`. Se você prefere
  contêineres, a página do [Docker](/telinha/pt-br/start/docker/) também serve
  para uma VPS.
- Um plano pequeno dá conta para começar: o servidor repassa o vídeo sem
  recodificar, então a rede pesa mais que CPU ou memória. Confira a franquia
  mensal de tráfego do plano, porque cada espectador recebe a transmissão
  inteira: veja
  [Quantas pessoas podem assistir?](/telinha/pt-br/faq/#quantas-pessoas-podem-assistir).
- Acesso às configurações de firewall do provedor (o nome muda: security
  group, security list ou firewall).
- Um servidor do Discord onde você pode criar um aplicativo e adicionar um bot.
  Dá para criar o aplicativo antes do setup ou durante ele: veja
  [Aplicativo do Discord](/telinha/pt-br/start/discord/).
- Um endereço: um domínio seu com um
  [registro A](/telinha/pt-br/guides/domains/#seu-próprio-domínio) apontando
  para a VPS, um nome
  gratuito do DuckDNS ou nenhum domínio, com o
  [sslip.io](/telinha/pt-br/guides/domains/#sslipio).
  [Endereço, HTTPS e modos de entrada](/telinha/pt-br/guides/domains/)
  compara as opções.

## Abra as portas primeiro

Faça isto antes da instalação: o setup testa as portas no final, e
muitos provedores só liberam o SSH por padrão. Uma VPS tem dois firewalls, e
os dois precisam deixar estas portas entrarem:

| Porta | Quando | Para quê |
| --- | --- | --- |
| TCP 7881 | sempre | Vídeo por TCP, para redes que bloqueiam UDP |
| UDP 7882 | sempre | Vídeo por UDP, o caminho normal |
| TCP 443 | domínio próprio, DuckDNS ou sslip.io | As páginas, por HTTPS |
| TCP 443 (TURN sobre TLS) | TURN ligado | A mesma porta: o vídeo retransmitido para quem está numa rede que só libera a 443; nada a mais para abrir |
| TCP 80 | idem, a não ser com `HTTP_PORT=0` | O desafio do Let's Encrypt e o redirecionamento para HTTPS |

Com um Cloudflare Tunnel só as duas portas de mídia são necessárias: túneis não
levam WebRTC. Se você vai escolher outra porta no setup, libere essa no
lugar.

:::note
Com o TURN ligado, o TURN do LiveKit escuta na `TURN_PORT` (5349) e
retransmite pela UDP 30000-40000, as duas só para uso dentro da máquina: o
Caddy chega na primeira da mesma máquina, e a retransmissão só fala com o
próprio LiveKit. Deixe as duas fechadas nos dois firewalls.
:::

**O firewall do provedor.** Crie uma regra de entrada para cada linha da tabela
no painel do provedor (security group, security list ou regras de firewall),
vinda de qualquer endereço.

**O firewall do próprio servidor.** A Telinha não cria regras de firewall no
Linux. Se o ufw ou o firewalld estiver ativo, libere as mesmas portas nele; com
as portas padrão:

```sh
sudo ufw allow 7881/tcp && sudo ufw allow 7882/udp && sudo ufw allow 443/tcp && sudo ufw allow 80/tcp
sudo firewall-cmd --permanent --add-port=7881/tcp --add-port=7882/udp --add-port=443/tcp --add-port=80/tcp && sudo firewall-cmd --reload
```

:::caution
Se for ligar o ufw agora, libere o SSH antes (`sudo ufw allow OpenSSH`), senão a
próxima conexão fica trancada para fora.
:::

:::note
Algumas imagens de provedor (as do Ubuntu na Oracle Cloud, por exemplo)
bloqueiam portas com regras do iptables puro, com o ufw desligado. Se
`sudo iptables -L INPUT -n` mostrar uma regra `REJECT`, siga o guia do provedor
para liberar as portas no servidor também.
:::

Numa VPS não há roteador, então o setup desliga o UPnP (`UPNP=off`).
[Encaminhamento de portas](/telinha/pt-br/guides/port-forwarding/) fala mais
sobre firewalls.

## Instalação

Numa VPS, instale como root: assim o serviço roda com um usuário de sistema
próprio, `telinha`, pode usar as portas 80 e 443 e continua rodando quando você
sai do SSH.

<Steps>

1. Conecte no servidor. O painel do provedor mostra o IP dele e o usuário
   para entrar (muitas vezes `root` ou `ubuntu`), com uma senha ou uma chave
   SSH. No Windows 10 ou 11 abra o PowerShell, no macOS ou no Linux abra o
   Terminal, e digite:

   ```sh
   ssh <usuário>@<IP do servidor>
   ```

   Na primeira vez ele pergunta se você confia na impressão digital
   (fingerprint) do servidor: responda `yes`. Depois rode, no servidor:

   ```sh
   curl -fsSL https://github.com/sombraSoft/telinha/releases/latest/download/install.sh | sudo sh
   ```

   (Se você entrou como root, tire o `sudo`.)

2. Ele pergunta se a Telinha vai rodar como programa nativo ou no Docker.
   Fique com o padrão, nativo.

3. O script baixa o `telinha-linux-x64.tar.gz` (ou o `telinha-linux-arm64.tar.gz`)
   e o `SHA256SUMS` da versão estável mais nova, para se o sha256 não bater,
   instala o programa e abre o `telinha setup`.

</Steps>

O programa vai para `/usr/local/lib/telinha/telinha`, chamado pelo comando
`/usr/local/bin/telinha`; a pasta da instalação é `/opt/telinha`, e o setup
copia o programa para `/opt/telinha/bin/` para o serviço, que atualiza essa
cópia sozinho. O script não baixa mais nada: o `livekit-server` e o `caddy` ou o
`cloudflared` vêm depois, o `livekit-server` e o `cloudflared` dos projetos
originais conferidos contra um sha256 fixo, o `caddy` da mesma versão da
Telinha conferido com o `SHA256SUMS` dela. Para pular a
pergunta, ponha `-s -- --native` depois do `sh` (`--no-setup` instala sem abrir
o setup). `TELINHA_VERSION` instala uma tag específica.

## Rode o setup

O setup ocupa o terminal com telas próprias: os passos na lateral esquerda
(Onde, Endereço, Discord, Portas, Atualizações, Revisão, Instalação), a
pergunta atual num cartão à direita e, ao lado ou embaixo, uma dica que explica
a escolha. Servidores, cargos e canais aparecem em listas, então você nunca
copia id na mão. Na primeira vez ele começa pelo idioma, português do Brasil ou
inglês, e todas as telas trocam na hora. Por SSH funciona igual, a partir de 80
colunas por 24 linhas.

- **Responda** com ↑ ↓ e Enter, ou aperte o número de uma opção. Numa resposta
  de texto, digite e aperte Enter.
- **Volte** com Esc ou ←. As respostas que você deu ficam.
- **Pule para um passo** com Tab: ↑ ↓ e Enter vão para qualquer passo já
  respondido, e Esc volta para o cartão.
- **Segredos** (tokens) aparecem como bolinhas. Cole com o atalho de colar do
  seu cliente SSH (Ctrl+V, muitas vezes Ctrl+Shift+V, ou o botão direito), e
  aperte Ctrl+R para mostrar ou esconder o que você colou.
- **Saia** com Ctrl+C. Nada é gravado até você aplicar na Revisão.

[Linha de comando](/telinha/pt-br/reference/cli/#teclas) lista todas as
teclas. Numa VPS, o caminho é este:

<Steps>

1. **Onde.** Para *Onde a Telinha vai rodar?* escolha *Um servidor alugado
   (VPS)*. Depois disso não tem pergunta sobre roteador.

2. **Endereço.** Ele pergunta *Como o pessoal vai chegar na Telinha?*: um
   domínio seu (o registro A é comparado com o IP público), DuckDNS, sslip.io,
   um Cloudflare Tunnel ou o seu próprio proxy reverso. Nas três primeiras
   opções a Telinha pega o certificado HTTPS pela 80 e pela 443, que você já
   liberou acima. Com o sslip.io ele usa o IPv4 público do servidor (e pergunta
   quando não consegue ver) e grava o endereço e o IP que o LiveKit anuncia:

   ```ini
   PUBLIC_URL=https://203-0-113-9.sslip.io
   LIVEKIT_NODE_IP=203.0.113.9
   ```

3. **Discord.** Cole o token do bot: a Telinha confere ele com o Discord na
   hora e lê o seu app a partir dele. Depois o segredo do cliente (também
   conferido), o servidor (uma lista dos que o bot já está; *Outro servidor*
   mostra um link de convite e confere de novo quando você adicionar o bot), o
   cargo que pode entrar, os canais (Espaço marca um, `a` marca todos) e o
   nome do comando. O nome do grupo é opcional. Quando o app ainda não tem o
   redirecionamento de login, um cartão mostra o endereço para adicionar em
   OAuth2 → Redirects, a única coisa que você faz na mão no Portal do
   Desenvolvedor: adicione, aperte Save Changes lá e escolha *Adicionei:
   verificar de novo*. [Aplicativo do Discord](/telinha/pt-br/start/discord/)
   mostra cada tela.

4. **Portas.** TCP 7881 e UDP 7882 levam o vídeo. Mantenha essas, a não ser
   que outro programa do servidor já use alguma. A dica lista as portas que o
   firewall do provedor precisa deixar entrar, com os comandos do ufw e do
   firewalld.

5. **Atualizações.** Diga que sim: as versões estáveis novas se instalam
   sozinhas quando nenhuma sala está aberta.

6. **Revisão.** Todas as respostas numa tela só, agrupadas por passo, com o
   endereço web em destaque e os segredos aparecendo apenas como definido,
   mantido ou gerado. Role com PgUp e PgDn quando a lista for longa. Escolha
   *Aplicar* (ou *Aplicar com um novo segredo de cookie*, oferecido numa nova
   rodada, que desconecta todo mundo das páginas), *Voltar pras perguntas* ou
   *Sair sem gravar*. Nada mudou neste servidor até você aplicar.

7. **Instalação.** Uma lista ao vivo: o app do Discord (conferido, com os
   intents ligados), o endereço do DuckDNS se você escolheu um, o
   `telinha.env` (`/opt/telinha/config/telinha.env`, do root e legível pelo
   serviço), os programas auxiliares (com uma barra para cada download), o
   serviço (a unidade do systemd), a linha de roteador e firewall, o início, o
   certificado HTTPS e as verificações finais. A linha de roteador e firewall
   lista as portas que o firewall do provedor precisa deixar entrar, com o
   comando do ufw ou do firewalld quando um deles está instalado. No fim a tela
   mostra o seu endereço web, e *Ver o diagnóstico* abre a lista de
   verificações com o teste pelo celular.

</Steps>

Se uma tarefa falha, as linhas dela se abrem embaixo com uma dica e três
escolhas: *Tentar de novo* roda ela outra vez, *Pular* deixa pra lá e segue com
o resto (as verificações finais dizem o que ficou faltando), e *Voltar pras
perguntas* leva à pergunta de que aquela tarefa depende (o token do bot para o
app do Discord, o token do DuckDNS para o DuckDNS) ou à Revisão; aplique de novo
de lá e os segredos gerados antes continuam os mesmos. Gravar o telinha.env não
tem *Pular*: tudo depois dele precisa do arquivo; depois de gravado, a Revisão
diz isso e a última escolha vira *Sair da configuração*. ↑ nas escolhas percorre
as linhas já terminadas, e Enter mostra o que cada uma fez. O último cartão abre
o que falta fazer à mão (as portas do roteador, o comando de um aviso), e o
resumo que fica no terminal também lista isso. Voltar fica desligado enquanto
uma tarefa roda, e Ctrl+C pede um segundo aperto, porque parar no meio pode
deixar uma instalação pela metade.

:::caution
O sslip.io é um domínio compartilhado: o Let's Encrypt pode recusar um
certificado na semana em que muitos já foram emitidos para ele. Um domínio seu,
ou o DuckDNS, é mais confiável.
:::

Se você rodou o instalador como usuário em vez de root, o passo Portas também
pergunta *Liberar elas com um comando sudo durante a instalação?*, porque um
usuário não consegue usar a 80 e a 443 sem isso. Diga que sim e, na linha do
serviço, as telas saem da frente enquanto o `sudo` pede a sua senha uma vez, e
voltam na mesma tarefa.

Sem terminal, ou com `--non-interactive`, o setup imprime linhas simples e tira
cada resposta das opções, do ambiente e do arquivo existente: veja
[Linha de comando](/telinha/pt-br/reference/cli/#telinha-setup).

## Redes rígidas

Algumas pessoas estão em redes que só deixam o navegador chegar na porta 443
(empresas, escolas, algumas operadoras de celular), onde as portas de mídia
nunca passam. Com o endereço na 443, a Telinha retransmite o vídeo delas por
`turn.<host>:443`, que para essas redes parece um site HTTPS qualquer:
[TURN sobre TLS na porta 443](/telinha/pt-br/guides/turn/). O passo Vídeo do
setup pergunta *Também passar o vídeo pela porta 443 para redes rígidas?* (sim
por padrão). Com um nome do DuckDNS ou do sslip.io é só isso; com domínio
próprio ele antes pede para você criar o registro DNS `turn.<host>`, onde
`<host>` é o host do `PUBLIC_URL` (para `https://telinha.example.com` fica
`turn.telinha.example.com`, veja [DNS](/telinha/pt-br/guides/turn/#dns)),
apontando para a VPS, e confere se ele resolve. A linha `turn` do doctor diz
se funciona.

## Verifique

```sh
sudo telinha doctor
```

O doctor é uma lista de verificações: uma linha para cada, com um spinner até
sair o resultado. Aperte Enter numa linha para ver os detalhes e, quando ela não
está ok, como corrigir; `r` roda todas de novo depois que você consertar algo.
Quando as verificações terminam, um painel mostra um link e um QR code para o
teste pelo celular: abra no celular com o Wi-Fi desligado, para o teste passar
pelos dados móveis, como a conexão de boa parte dos seus amigos. Ele diz se a
página, a conexão com o LiveKit, o UDP e o TCP funcionam de lá, e com o TURN
ligado se o vídeo consegue passar por `turn.<host>:443` (a linha TURN/TLS
443); `p` começa um novo teste; um primeiro caminho para um IP que não é o IP público da VPS quer
dizer um `LIVEKIT_NODE_IP` errado.
[Doctor e solução de problemas](/telinha/pt-br/guides/doctor/) explica cada
linha e o que uma falha quer dizer.

## Use

Digite `/telinha` (ou o nome de comando que você escolheu) num dos canais
escolhidos. O bot posta um card com um botão para uma sala nova em
`https://<seu endereço>/r/<código>`. Quem abre faz login com o Discord uma vez, e
quem tem o cargo entra. Compartilhe a tela pelo Chrome, pelo Edge ou outro
navegador baseado em Chromium; assistir funciona no celular também. O card
mostra quem está transmitindo e quem está assistindo, e a sala fecha sozinha
alguns minutos depois que todo mundo sai.

## No dia a dia

O serviço inicia com a máquina, sobe a Telinha de novo depois de uma
atualização ou de um travamento e grava o log no journal:

```sh
sudo telinha service status
sudo telinha service restart
journalctl -u telinha -f
```

O `systemctl` gerencia a unidade `telinha` como qualquer outra;
`telinha service start`, `stop`, `restart` e `status` fazem as mesmas chamadas.

**As atualizações** acontecem sozinhas: a Telinha confere alguns minutos depois
de iniciar e depois a cada poucas horas, espera enquanto há salas abertas,
confere o sha256 e volta para a versão anterior se a nova não subir.
`sudo telinha update --check` mostra a situação e `sudo telinha update --now`
instala na hora. Veja [Atualizações](/telinha/pt-br/guides/updates/).

**Mudar as configurações** é rodar o `sudo telinha setup` de novo: cada pergunta
já vem com o valor atual, os segredos podem ser mantidos (Enter mantém) e o serviço reinicia
com o arquivo novo. Editar o `/opt/telinha/config/telinha.env` na mão também
funciona, seguido de `sudo telinha service restart`.

**Para remover**: `sudo telinha service uninstall` tira a unidade e mantém os
arquivos; depois apague `/opt/telinha`.

[Rodando como serviço](/telinha/pt-br/guides/service/) tem os detalhes.
