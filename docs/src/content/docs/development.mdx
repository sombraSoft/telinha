You only need [mise](https://mise.jdx.dev/getting-started.html), activated in your shell. It works on Windows and Linux. `mise install` installs the versions `mise.toml` pins (Bun, Go and the linters CI runs), then the dependencies with `bun install`; run it again after a pull.

## Run from a clone

Use a clone for development, or on a platform without a release build. Run from source there is no service install and no self-update: update with `git pull`, `mise install`, `bun run build`, then restart.

```
git clone https://github.com/sombraSoft/telinha && cd telinha
mise install && bun run build
bun server/src/index.ts setup    # same setup; downloads the helper binaries into <home>/bin
bun server/src/index.ts          # run in this console
```

## Scripts

```
mise install
bun run dev
bun run typecheck
bun run test
bun run build
bun run e2e
bun run image
bun run bins
bun run caddy
bun run versions check
bun run compile --smoke
bun run docs:dev
bun run docs:build
```

| Script | What it does |
| --- | --- |
| `bun run dev` | Vite with hot reload plus the Bun server, which runs LiveKit; open `http://localhost:5173/r/` |
| `bun run typecheck` | `tsc` and `svelte-check` over every package, including `docs/scripts` |
| `bun run test` | `bun test` over the server, the web page and the docs |
| `bun run build` | Builds the room page into `web/dist` |
| `bun run e2e` | Playwright; run `bun run build` first, and install a Chromium with `bunx playwright install chromium` |
| `bun run image` | Builds `telinha:dev` with docker or podman (Caddy is compiled in a Go stage of the `Dockerfile`), then runs the smoke test, which also checks the Caddy version and modules and has Caddy validate the DuckDNS `Caddyfile` |
| `bun run bins` | Downloads the three helper binaries for this host into `.cache/telinha/bin`: `livekit-server` and `cloudflared` from upstream, `caddy` from the newest Telinha release (`bun scripts/bins.ts --release vX.Y.Z caddy` takes another release's). A release without a `caddy` asset is a warning, not a failure, when caddy was not named; build it with `bun run caddy` instead |
| `bun run caddy` | Builds Telinha's Caddy (upstream Caddy plus the modules in `versions.json`) with xcaddy into `.cache/telinha/bin` (or `BIN_DIR`, or `--out DIR`), next to what `bun run bins` downloads; it uses the Go that mise installs. On the host's own platform it also checks the version and the modules |
| `bun run versions check` | Validates `versions.json` (`refresh` recomputes the livekit and cloudflared hashes) |
| `bun run compile --smoke` | Builds the native binaries for this OS into `dist-bin/` (run `bun run build` first) |
| `bun run docs:dev` | Serves this site at `http://localhost:4321/telinha/` |
| `bun run docs:build` | Builds this site into `docs/dist/` |

### The dev server

`bun run dev` downloads `livekit-server` (pinned in `versions.json`, sha256-verified) on first run and starts the server with `TELINHA_HOME=.cache/telinha`, `INGRESS=external`, `MEDIA=self`, `LIVEKIT_NODE_IP=127.0.0.1`, `UPNP=off` and `AUTO_UPDATE=off`. The server supervises LiveKit exactly as in production. Vite proxies `/auth` and `/livekit` (WebSocket included) to the server on `127.0.0.1:8081`, so the browser goes through the real gate and signaling relay.

The server runs with `DEV_USER` set (default `1:Dev`, that is `<id>:<name>`), a fake login that skips Discord and the bot. It is refused unless `PUBLIC_URL` is `http://localhost` or `http://127.0.0.1`, `LISTEN` is a loopback address and `INGRESS` is `external`, and in that mode every request whose `Host` is not `localhost`, `127.0.0.1` or `[::1]` gets a 421. Set `DEV_LOCALE=en` or `pt-BR` to force the language. There is no slash command in dev, so any valid room code (`/r/lamo-futi`, `/r/bada-kodi`: two or three consonant-vowel syllables on each side of the dash) opens a room on first use. `CLOSE_EMPTY_SECONDS=30 bun run dev` shows a room closing.

### Terminal screens

The setup and doctor screens under `server/src/tui` are `.tsx` files (OpenTUI with Solid); `server/tsconfig.json` and `docs/scripts/tsconfig.json` set `"jsx": "preserve"` and `"jsxImportSource": "@opentui/solid"`. Bun runs that JSX only through OpenTUI's Solid transform: `bun test` loads it from the `[test]` preload in `bunfig.toml` and `server/bunfig.toml`, a run from source registers it with `prepareTui()` (`server/src/tui/load.ts`), and the native build applies it as a plugin. `server/test/tui-*.test.tsx` draw the screens in a test terminal and compare frame snapshots; `bun test server/test/tui-setup-frames.test.tsx -u` rewrites them after an intended change. `TELINHA_THEME=light` or `dark` forces the colours, and `TELINHA_SMOKE_TUI=1 bun server/src/index.ts --version` runs the terminal UI smoke from source.

## Native binaries

`bun run compile` (`scripts/build-binary.ts`) compiles with `Bun.build` (its `compile` option, plus the Solid plugin for the terminal screens) with `web/dist` embedded (run `bun run build` first). It writes `dist-bin/<target>/telinha[.exe]`, the release archives `dist-bin/telinha-linux-{x64,arm64}.tar.gz` and `dist-bin/telinha-windows-{x64,arm64}.zip` (each with `LICENSE`, the Windows ones also with `telinha-tray.exe` when given `--tray`) and `dist-bin/SHA256SUMS`.

| Option | Meaning |
| --- | --- |
| `--target` | `linux-x64`, `linux-arm64`, `windows-x64`, `windows-arm64`, `linux`, `windows` or `host`; repeatable, default is this OS's two targets |
| `--version X.Y.Z` | Version to embed, default from `package.json` |
| `--out DIR` | Output directory |
| `--smoke` | Runs the host binary's `--version`, then its terminal UI smoke, and checks each binary's size and that no Babel got bundled |
| `--tray PATH` | The `telinha-tray.exe` to put into the Windows zips |
| `--no-pack` | Compiles only: no archives, no `SHA256SUMS` |

`bun run compile pack --target windows --from DIR` archives binaries built earlier, `DIR/<target>/telinha.exe` and `DIR/tray/telinha-tray.exe` (or `--tray PATH`), without compiling; the release workflow uses it to pack the Windows programs after they are signed. `bun run compile sums` rewrites `SHA256SUMS` for whatever archives are in `dist-bin/`, the `caddy-<target>` ones included. `bun run compile pack-caddy --target <t> --from DIR` packs a built `caddy` as the release archive for that target; the release workflow builds each one through the `Dockerfile`'s `caddy-export` stage. Linux targets cross-compile from any host once `bun install --os='*' --cpu='*'` has fetched every target's OpenTUI native package. Windows targets build only on Windows, where Bun can write their version resource. The x64 targets are Bun's baseline builds. The binary never reads a `.env` or `bunfig.toml` from the directory it runs in.

## Tray icon

The [Windows tray icon](/telinha/guides/tray/) lives in `tray/`: C# on the .NET Framework 4.8 (WinForms), one `telinha-tray.exe` with no DLL next to it. It builds on Windows with the .NET SDK (8 or newer) and no Visual Studio:

```
dotnet test tray/tests/telinha-tray.tests.csproj -c Release
dotnet build tray/telinha-tray.csproj -c Release -p:Version=0.7.0
bun scripts/tray-icon.ts
bun run compile --tray tray/bin/Release/net48/telinha-tray.exe
```

| Command | What it does |
| --- | --- |
| `dotnet test …` | Builds the tray and runs its MSTest unit tests (`tray/tests/`) |
| `dotnet build …` | Writes `tray/bin/Release/net48/telinha-tray.exe`. `-p:Version` sets the version (default `0.0.0`), so its `ProductVersion` and `telinha-tray --version` match `telinha --version`; run it after the tests, which rebuild without it |
| `bun scripts/tray-icon.ts` | Draws `tray/telinha.ico` from the site's favicon shapes; the output is the same every run |
| `bun run compile --tray …` | The native binaries, with the tray in the Windows zips |

To try a build against a running Telinha, copy `telinha-tray.exe` into `<home>\bin` and start it with `telinha tray start` from a normal terminal; the tray refuses to run elevated.

## This site

The site is [Starlight](https://starlight.astro.build) in the `docs/` workspace, in English (the root language) and Brazilian Portuguese, with every page in both languages.

- **Where the pages live.** English pages are under `docs/src/content/docs/`, Portuguese ones at the same path under `docs/src/content/docs/pt-br/`. Page order inside a sidebar group comes from `sidebar: { order: N }` in the frontmatter. Pages that use a component are `.mdx`, the others `.md`.
- **Links.** The site is served under `/telinha/`, so internal links carry it: `/telinha/start/choose/` in English, `/telinha/pt-br/start/choose/` in Portuguese, always with the trailing slash. The link validator fails the build on a broken link, a broken anchor, a page that exists in only one language or a link from one language to the other.
- **Generated reference.** The [configuration](/telinha/reference/configuration/), command line and doctor checks pages are built from the code. `docs/scripts/generate.ts` reads the real config keys, flags and checks and writes `docs/src/data/generated.json` (not committed) before every dev or build run. The descriptions are written by hand in `docs/src/data/reference.ts`, keyed by the same names.
- **Drift tests.** `docs/scripts/reference.test.ts` runs under `bun run test` and fails when a key, flag, command or check in the code has no description, when a description names something that no longer exists, when a language is missing a page, or when a page mentions an unknown environment key or flag.
- **Add a language.** Add a folder under `docs/src/content/docs/` with the same page tree, one line in `locales` in `docs/astro.config.mjs`, and a `translations` entry for every sidebar group and link there.
- **Add a router page.** Add one file under `routers/` in each language, with the same headings, a `sidebar: { order: N }` and a sources list at the end. The sidebar group lists it by itself.

`bun run docs:dev` and `bun run docs:build` both run the generator first.

### Publishing

`release.yml` calls `.github/workflows/docs.yml` after it publishes a stable release (pre-releases do not publish the site), so the site follows each release. You can also run `docs.yml` by hand from the Actions tab on `main`, to publish a documentation fix between releases.
