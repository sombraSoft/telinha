A mini PC, a Raspberry Pi 4 or 5, an old laptop or a home server: any 64-bit
Linux machine that stays on. One `curl` line installs Telinha, the setup
screens ask a few questions, and systemd keeps it running.

## Before you start

- 64-bit Linux with glibc (Debian, Ubuntu, Raspberry Pi OS 64-bit, Fedora and
  the like) on x64 or arm64, with systemd. The x64 build runs on any x86-64
  CPU, old Celeron and Atom boxes included. On Alpine or another musl system
  the installer switches to [Docker](/telinha/start/docker/); a 32-bit
  Raspberry Pi OS is refused, install the 64-bit one.
- `curl` or `wget`, `tar`, and `sha256sum` or `shasum`.
- A Discord server where you can create an application and add a bot. You can
  create the app before the setup or while it runs: see
  [Discord app](/telinha/start/discord/).
- For the address people open: a domain on Cloudflare, or nothing, in which
  case setup gives you a free DuckDNS address.
  [Address, HTTPS and ingress modes](/telinha/guides/domains/) compares the
  two.
- Access to your router's admin page, unless it does UPnP (many routers ship
  with it off, and ISP routers often hide the switch). Telinha never needs
  ports 80 or 443 at home: only the two media ports, plus 8443 with a DuckDNS
  address.
  No access and no UPnP, for example a locked ISP router or a shared building
  network? Then this machine cannot open the ports itself: ask the ISP or
  whoever runs the network to forward them, or use a [VPS](/telinha/start/vps/).
  If your line is behind CGNAT, nothing from the internet reaches the
  machine: read
  [CGNAT and double NAT](/telinha/guides/domains/#cgnat-and-double-nat) first.

## Install

Decide first whether Telinha is installed as root or as your user. Both use
the same one-liner; `sudo` makes the difference.

| | As root | As your user |
| --- | --- | --- |
| Home folder | `/opt/telinha` | `~/.local/share/telinha` (`$XDG_DATA_HOME` respected) |
| Service | System unit `/etc/systemd/system/telinha.service`, running as a `telinha` system user | User unit `~/.config/systemd/user/telinha.service` |
| Keeps running after you log out | Yes | Only with lingering (the setup turns it on) |
| Commands | `sudo telinha ...` | `telinha ...` |

On a machine that is there for Telinha, the root install is the simpler one.

<Steps>

1. Run the installer, as root:

   ```sh
   curl -fsSL https://github.com/sombraSoft/telinha/releases/latest/download/install.sh | sudo sh
   ```

   or as your user:

   ```sh
   curl -fsSL https://github.com/sombraSoft/telinha/releases/latest/download/install.sh | sh
   ```

2. It asks whether to run Telinha as a native program or in Docker. Keep the
   default, native.

3. The script downloads `telinha-linux-x64.tar.gz` (or `telinha-linux-arm64.tar.gz`)
   and `SHA256SUMS` from the newest stable release, stops if the sha256 does
   not match, installs the program and starts `telinha setup`.

</Steps>

As root it installs a root-owned `/usr/local/lib/telinha/telinha`, run by the
`/usr/local/bin/telinha` command, and the setup copies it into
`/opt/telinha/bin/` for the service, which updates that copy itself. As your
user it installs `~/.local/share/telinha/bin/telinha` and prints the line to
add to `~/.profile` so the `telinha` command is found:

```sh
export PATH="$HOME/.local/share/telinha/bin:$PATH"
```

The script downloads nothing else: `livekit-server` and `caddy` or
`cloudflared` come later, `livekit-server` and `cloudflared` from upstream
checked against a pinned sha256, `caddy` from the same Telinha release checked
against its `SHA256SUMS`. To skip the
question, add `-s -- --native` after `sh` (`--no-setup` installs without
starting the setup), or set `TELINHA_INSTALL=native`. `TELINHA_VERSION`
installs a given release tag and `TELINHA_HOME` another home folder.

## Run the setup

Setup fills the terminal with its own screens: the steps down the left (Where,
Address, Discord, Ports, Updates, Review, Install), the current question as a
card on the right and, beside or under it, a hint that explains the choice.
Servers, roles and channels come from lists, so you never copy an id by hand.
A first run starts with the language, English or Brazilian Portuguese, and
every screen switches at once. Over SSH it works the same, from 80 columns by
24 rows.

- **Answer** with ↑ ↓ and Enter, or press the number of an option. For a text
  answer, type and press Enter.
- **Go back** with Esc or ←. The answers you gave stay.
- **Jump** with Tab: ↑ ↓ and Enter go to any step you have already answered,
  and Esc returns to the card.
- **Secrets** (tokens) show as dots. Paste with your terminal's paste shortcut
  (Ctrl+V, often Ctrl+Shift+V), and press Ctrl+R to show or hide what you
  pasted.
- **Quit** with Ctrl+C. Nothing is written until you apply at the Review.

[Command line](/telinha/reference/cli/#keys) lists every key. On a Linux box at
home it goes like this:

<Steps>

1. **Where.** The hint shows the public IP and the router, if one answers
   UPnP, NAT-PMP or PCP. Choose *A computer at home (a PC or a home server)*
   for *Where will Telinha run?*

2. **Address.** Home internet connections usually do not let the web ports
   80 and 443 in, so Telinha does not count on them. It asks *Do you have a
   domain on Cloudflare?*

   - *Yes: use a Cloudflare Tunnel.* Your own address, and nothing to open
     for the pages. You paste the tunnel's token and its public hostname; see
     [Cloudflare Tunnel](/telinha/guides/domains/#cloudflare-tunnel).
   - *No: use a free DuckDNS address.* You sign in on duckdns.org, add a name
     and paste the token, which is tried at once. Telinha serves HTTPS on port
     8443 (you can pick another) and gets the certificate through DuckDNS, so
     the address looks like `https://my-group.duckdns.org:8443` and the links
     carry the port. Some strict networks (offices, schools) only let browsers
     reach port 443, so people there cannot open them; a domain on Cloudflare
     has no such limit. See
     [DuckDNS on port 8443](/telinha/guides/domains/#duckdns-on-port-8443).

3. **Discord.** Paste the bot token: Telinha checks it with Discord right
   away and reads your app from it. Then the client secret (also checked), the
   server (a list of the ones the bot is in; *Another server* shows an invite
   link and checks again once you added the bot), the role that may enter, the
   channels (Space marks one, `a` marks all) and the command name. A group
   name is optional. When the app does not have the login redirect yet, a card
   shows the address to add under OAuth2 → Redirects, the one thing you do by
   hand on the Developer Portal: add it, press Save Changes there, then choose
   *I added it: check again*. [Discord app](/telinha/start/discord/) walks
   through every screen.

4. **Video.** *Where does the video go through?* Keep *This computer*.
   *LiveKit Cloud* is for a connection that nothing from the internet can
   reach (CGNAT, which the setup detects and then picks Cloud for you): it
   asks the project's URL, API key and secret, and there are no media ports to
   open; see [LiveKit Cloud](/telinha/guides/livekit-cloud/).

5. **Ports.** TCP 7881 and UDP 7882 carry the video. Keep them unless
   something else on the machine uses them. Then *Ask the router?*: say yes to
   let Telinha ask the router for the ports through UPnP, or no if you will
   forward them yourself.

6. **Updates.** Say yes: new stable releases then install themselves when no
   room is open.

7. **Review.** Every answer on one screen, grouped by step, with the web
   address highlighted and secrets shown only as set, kept or generated. Page
   with PgUp and PgDn when the list is long. Choose *Apply* (or *Apply with a
   new cookie secret*, offered on a re-run, which logs everyone out of the
   pages), *Back to the questions* or *Quit without writing*. Nothing has
   changed on this machine until you apply.

8. **Install.** A live list: the Discord app (checked, and its intents
   switched on), the DuckDNS address if you picked one, `telinha.env`, the
   helper programs (with a bar for each download), the service, the router and
   firewall, the start, the HTTPS certificate (with a DuckDNS address) and the
   final checks. The file goes to `config/telinha.env` in the home folder:
   owned by root and readable by the service in a root install, mode 0600 in a
   user install. The service row installs and starts the systemd unit; as your
   user it also turns lingering on, so Telinha keeps running after you log out
   (when that needs a password it prints `sudo loginctl enable-linger <you>` for
   you to run). The router row looks at the router (warning about CGNAT or
   double NAT, listing the ports to forward by hand without UPnP), then
   Telinha starts and its certificate arrives. At the end the screen shows
   your web address, and *Show the doctor report* opens the checklist with the
   phone test.

</Steps>

If a task fails, its lines open under it with a hint, and three choices:
*Retry* runs it again, *Skip* leaves it and goes on with the rest (the
final checks then tell you what is missing), and *Back to questions* returns
to the question that task depends on (the bot token for the Discord app, the
DuckDNS token for DuckDNS) or to the Review; apply again from there and the
secrets generated before stay the same. Writing telinha.env has no *Skip*:
everything after it needs the file; once it is written, the Review says so and
its last choice is *Leave setup*. ↑ from the choices walks the finished rows,
and Enter shows what each did. The last card opens what is left to do by hand
(the router's ports, a warning's command), and the summary left in the terminal
lists it too. Going back is off while a task runs, and Ctrl+C asks for a second
press, because stopping half way can leave a half install.

:::note[Forwarding the ports by hand?]
When no router answered UPnP (or you did not allow it), the router row only
lists the ports to forward and the install carries on, so the phone test fails
in the doctor report. That is expected: forward the ports as in
[Open the ports](#open-the-ports) below, then run `telinha doctor` again. The
certificate does not wait for them: with a DuckDNS address it comes through
DuckDNS (usually 1-3 minutes), and with a tunnel Cloudflare holds it.
:::

A user install binds no port below 1024 at home (8443 and the media ports are
all above it), so nothing needs root. If a setup ever does need one (an
advanced home answer that keeps 80 and 443), the Ports step asks *Allow them
with one sudo command during the install?*: answer yes and the screens step
aside while `sudo` asks for your password once, then come back on the same
task.

Without a terminal, or with `--non-interactive`, setup prints plain lines and
takes every answer from flags, the environment and the existing file: see
[Command line](/telinha/reference/cli/#telinha-setup).

## Open the ports

The internet has to reach the machine on these ports:

| Port | When | What for |
| --- | --- | --- |
| TCP 7881 | always | Video over TCP, for networks that block UDP |
| UDP 7882 | always | Video over UDP, the normal path |
| TCP 8443 | DuckDNS address (your port if you changed it) | The pages, over HTTPS |

Nothing more: not 80, not 443. With a Cloudflare Tunnel only the two media
ports are needed (tunnels do not carry WebRTC). If you changed a port in the
setup, use your value.

**UPnP first.** When the router answered and you allowed it, Telinha asks the
router for these ports while it runs and you have nothing to do. Otherwise
forward them by hand to the machine's local IP, after giving the machine a
fixed address so the rule keeps pointing at it.
[Port forwarding](/telinha/guides/port-forwarding/) explains both, and there
are pages for [Vivo](/telinha/routers/vivo/), [Claro](/telinha/routers/claro/),
[TIM](/telinha/routers/tim/) and [Oi](/telinha/routers/oi/) routers.

**The machine's own firewall.** Telinha adds no firewall rules on Linux. If
ufw or firewalld is active, open the same ports there. With the default ports
and a DuckDNS address (drop `8443/tcp` with a tunnel):

```sh
sudo ufw allow 7881/tcp && sudo ufw allow 7882/udp && sudo ufw allow 8443/tcp
sudo firewall-cmd --permanent --add-port=7881/tcp --add-port=7882/udp --add-port=8443/tcp && sudo firewall-cmd --reload
```

`telinha doctor` prints these commands with your own ports when it finds
either tool.

## Check it

```sh
sudo telinha doctor
```

(`telinha doctor`, without `sudo`, for a user install.) Doctor is a checklist:
one row per check, each with a spinner until it has its result. Press Enter on
a row to see its detail and, when it is not ok, the fix; `r` runs every check
again after you fix something. When the checks are done a panel shows a link
and a QR code for the phone test: open it on your phone with Wi-Fi off, so the
test comes from outside your network like your friends' connections do. It
tells you whether the page, the LiveKit connection, UDP and TCP all work from
there, and `p` starts a new test. `telinha doctor --local` skips the checks
that need the internet.
[Doctor and troubleshooting](/telinha/guides/doctor/) explains every row and
what a failure means.

## Use it

Type `/telinha` (or the command name you chose) in one of the channels you
picked. The bot posts a card with a button to a new room at
`https://<your address>/r/<code>`. Whoever opens it logs in with Discord once,
and members with the role get in. Share your screen from Chrome, Edge or
another Chromium browser; watching works on phones too. The card shows who is
streaming and, while someone streams, who else is in the room. The room closes
by itself a few minutes after everyone leaves.

:::caution[It works for friends but not from your own network?]
Many routers cannot send a connection to their own public address back inside
(NAT loopback, also called hairpin NAT or NAT reflection). Then the room opens
on mobile data and for everyone outside, but not from this machine or another
device on your network. Turn NAT loopback on if the router has the option.
A hosts-file line pointing the name at the machine's local IP does not fix it:
the page loads, but LiveKit still announces the public IP for the video. See
[Doctor and troubleshooting](/telinha/guides/doctor/#works-from-outside-but-not-from-your-own-network).
:::

## Day two

The service starts at boot, starts Telinha again after an update or a crash,
and logs to the journal. For a root install:

```sh
sudo telinha service status
sudo telinha service restart
journalctl -u telinha -f
```

For a user install:

```sh
telinha service status
telinha service restart
journalctl --user -u telinha -f
```

`systemctl` (or `systemctl --user`) manages the `telinha` unit like any other;
`telinha service start`, `stop`, `restart` and `status` make the same calls.

**Updates** happen on their own: Telinha checks a few minutes after it starts
and then every few hours, waits while rooms are open, checks the sha256 and
rolls back a version that fails to start. `telinha update --check` shows where
you stand and `telinha update --now` installs at once (with `sudo` for a root
install). See [Updates](/telinha/guides/updates/).

**Changing settings** means running `telinha setup` again (`sudo telinha setup`
as root): every question starts at the current value, secrets can be kept (Enter keeps them), and
the service restarts with the new file. Editing `telinha.env` by hand works
too, followed by `telinha service restart`.

**Removing it**: `telinha service uninstall` removes the unit and keeps the
files; then delete the home folder.

[Running as a service](/telinha/guides/service/) has the details.
