A VPS has its own public IPv4, so there is no router to configure and CGNAT
does not matter. You open the ports in the provider's firewall instead. Without
a domain, sslip.io gives the server an HTTPS name made from its IP.

## Before you start

- A VPS with a current 64-bit Ubuntu LTS or Debian image (Fedora and other
  distributions with systemd work too), x64 or arm64, with a public IPv4 and a login as
  root or as a user with `sudo`. If you prefer containers, the
  [Docker](/telinha/start/docker/) page works on a VPS too.
- A small plan is enough to start: the server forwards the video without
  re-encoding it, so the network matters more than CPU or RAM. Check the
  plan's monthly transfer allowance, because every viewer receives the full
  stream: see [How many people can watch?](/telinha/faq/#how-many-people-can-watch).
- Access to the provider's firewall settings (called security group, security
  list or firewall, depending on the provider).
- A Discord server where you can create an application and add a bot. You can
  create the app before the setup or while it runs: see
  [Discord app](/telinha/start/discord/).
- An address: your own domain with an
  [A record](/telinha/guides/domains/#your-own-domain) pointing at the VPS, a free
  DuckDNS name, or no domain at all with
  [sslip.io](/telinha/guides/domains/#sslipio).
  [Address, HTTPS and ingress modes](/telinha/guides/domains/) compares them.

## Open the ports first

Do this before the install: the setup checks the ports at the end, and many
providers allow only SSH by default. A VPS has two firewalls, and both must
let these ports in:

| Port | When | What for |
| --- | --- | --- |
| TCP 7881 | always | Video over TCP, for networks that block UDP |
| UDP 7882 | always | Video over UDP, the normal path |
| TCP 443 | your own domain, DuckDNS or sslip.io | The pages, over HTTPS |
| TCP 443 (TURN over TLS) | TURN on | The same port: video relayed for viewers on networks that only allow 443; nothing more to open |
| TCP 80 | same, unless `HTTP_PORT=0` | The Let's Encrypt challenge and the redirect to HTTPS |

With a Cloudflare Tunnel only the two media ports are needed: tunnels do not
carry WebRTC. If you will pick another port in the setup, open that one
instead.

:::note
With TURN on, LiveKit's TURN listens on `TURN_PORT` (5349) and relays on UDP
30000-40000, both for use inside the machine only: Caddy reaches the first
from the same machine, and the relay talks only to LiveKit itself. Leave them
closed in both firewalls.
:::

**The provider's firewall.** Add an inbound rule per line of the table in the
provider's panel (security group, security list or firewall rules), from
any source address.

**The server's own firewall.** Telinha adds no firewall rules on Linux. If ufw
or firewalld is active, open the same ports there; with the default ports:

```sh
sudo ufw allow 7881/tcp && sudo ufw allow 7882/udp && sudo ufw allow 443/tcp && sudo ufw allow 80/tcp
sudo firewall-cmd --permanent --add-port=7881/tcp --add-port=7882/udp --add-port=443/tcp --add-port=80/tcp && sudo firewall-cmd --reload
```

:::caution
If you turn ufw on now, allow SSH first (`sudo ufw allow OpenSSH`), or the
next connection is locked out.
:::

:::note
Some provider images (Oracle Cloud's Ubuntu images, for example) block ports
with plain iptables rules while ufw stays inactive. If
`sudo iptables -L INPUT -n` lists a `REJECT` rule, follow the provider's guide
to open the ports on the server too.
:::

There is no router on a VPS, so the setup turns UPnP off (`UPNP=off`).
[Port forwarding](/telinha/guides/port-forwarding/) has more on firewalls.

## Install

On a VPS, install as root: the service then runs as its own `telinha` system
user, can bind ports 80 and 443, and keeps running when you log out.

<Steps>

1. Connect to the server. The provider's panel shows its IP address and the
   user to log in as (often `root` or `ubuntu`), with a password or an SSH
   key. On Windows 10 or 11 open PowerShell, on macOS or Linux open Terminal,
   and type:

   ```sh
   ssh <user>@<server IP>
   ```

   The first time it asks whether to trust the server's fingerprint: answer
   `yes`. Then run, on the server:

   ```sh
   curl -fsSL https://github.com/sombraSoft/telinha/releases/latest/download/install.sh | sudo sh
   ```

   (Logged in as root, drop the `sudo`.)

2. It asks whether to run Telinha as a native program or in Docker. Keep the
   default, native.

3. The script downloads `telinha-linux-x64.tar.gz` (or `telinha-linux-arm64.tar.gz`)
   and `SHA256SUMS` from the newest stable release, stops if the sha256 does
   not match, installs the program and starts `telinha setup`.

</Steps>

The program lands in `/usr/local/lib/telinha/telinha`, run by the
`/usr/local/bin/telinha` command; the home folder is `/opt/telinha`, and the
setup copies the program into `/opt/telinha/bin/` for the service, which
updates that copy itself. The script downloads nothing else: `livekit-server`
and `caddy` or `cloudflared` come later, `livekit-server` and `cloudflared`
from upstream checked against a pinned sha256, `caddy` from the same Telinha
release checked against its `SHA256SUMS`.
To skip the question, add `-s -- --native` after `sh` (`--no-setup` installs
without starting the setup). `TELINHA_VERSION` installs a given release tag.

## Run the setup

Setup fills the terminal with its own screens: the steps down the left (Where,
Address, Discord, Ports, Updates, Review, Install), the current question as a
card on the right and, beside or under it, a hint that explains the choice.
Servers, roles and channels come from lists, so you never copy an id by hand.
A first run starts with the language, English or Brazilian Portuguese, and
every screen switches at once. Over SSH it works the same, from 80 columns by
24 rows.

- **Answer** with ↑ ↓ and Enter, or press the number of an option. For a text
  answer, type and press Enter.
- **Go back** with Esc or ←. The answers you gave stay.
- **Jump** with Tab: ↑ ↓ and Enter go to any step you have already answered,
  and Esc returns to the card.
- **Secrets** (tokens) show as dots. Paste with your SSH client's paste
  shortcut (Ctrl+V, often Ctrl+Shift+V, or right-click), and press Ctrl+R to
  show or hide what you pasted.
- **Quit** with Ctrl+C. Nothing is written until you apply at the Review.

[Command line](/telinha/reference/cli/#keys) lists every key. On a VPS it goes
like this:

<Steps>

1. **Where.** Choose *A rented server (VPS)* for *Where will Telinha run?*
   There is no router question after this one.

2. **Address.** It asks *How will people reach Telinha?*: your own domain
   (its A record is compared with the public IP), DuckDNS, sslip.io, a
   Cloudflare Tunnel or your own reverse proxy. With the first three Telinha
   gets the HTTPS certificate over 80 and 443, which you opened above. With
   sslip.io it takes the server's public IPv4 (and asks for it when it cannot
   see it) and writes both the address and the IP LiveKit announces:

   ```ini
   PUBLIC_URL=https://203-0-113-9.sslip.io
   LIVEKIT_NODE_IP=203.0.113.9
   ```

3. **Discord.** Paste the bot token: Telinha checks it with Discord right
   away and reads your app from it. Then the client secret (also checked), the
   server (a list of the ones the bot is in; *Another server* shows an invite
   link and checks again once you added the bot), the role that may enter, the
   channels (Space marks one, `a` marks all) and the command name. A group
   name is optional. When the app does not have the login redirect yet, a card
   shows the address to add under OAuth2 → Redirects, the one thing you do by
   hand on the Developer Portal: add it, press Save Changes there, then choose
   *I added it: check again*. [Discord app](/telinha/start/discord/) walks
   through every screen.

4. **Video.** *Where does the video go through?* Keep *This computer*
   (*LiveKit Cloud* asks its project's URL, API key and secret instead; see
   [LiveKit Cloud](/telinha/guides/livekit-cloud/)). With the address on
   443, it then asks *Also serve video through port 443 for strict
   networks?*: say yes (see [Strict networks](#strict-networks) below). With
   your own domain, add the DNS record it shows first, `turn.<host>` pointing
   at the VPS; yes checks that it resolves.

5. **Ports.** TCP 7881 and UDP 7882 carry the video. Keep them unless
   something else on the server uses them. The hint lists the ports the
   provider's firewall must let in, with the ufw and firewalld commands.

6. **Updates.** Say yes: new stable releases then install themselves when no
   room is open.

7. **Review.** Every answer on one screen, grouped by step, with the web
   address highlighted and secrets shown only as set, kept or generated. Page
   with PgUp and PgDn when the list is long. Choose *Apply* (or *Apply with a
   new cookie secret*, offered on a re-run, which logs everyone out of the
   pages), *Back to the questions* or *Quit without writing*. Nothing has
   changed on this server until you apply.

8. **Install.** A live list: the Discord app (checked, and its intents
   switched on), the DuckDNS address if you picked one, `telinha.env`
   (`/opt/telinha/config/telinha.env`, owned by root and readable by the
   service), the helper programs (with a bar for each download), the service
   (the systemd unit), the router and firewall row, the start, the HTTPS
   certificate and the final checks. The router and firewall row lists the
   ports the provider's firewall must allow, with the ufw or firewalld command
   when one is installed. At the end the screen shows your web address, and *Show the doctor report* opens
   the checklist with the phone test.

</Steps>

If a task fails, its lines open under it with a hint, and three choices:
*Retry* runs it again, *Skip* leaves it and goes on with the rest (the
final checks then tell you what is missing), and *Back to questions* returns
to the question that task depends on (the bot token for the Discord app, the
DuckDNS token for DuckDNS) or to the Review; apply again from there and the
secrets generated before stay the same. Writing telinha.env has no *Skip*:
everything after it needs the file; once it is written, the Review says so and
its last choice is *Leave setup*. ↑ from the choices walks the finished rows,
and Enter shows what each did. The last card opens what is left to do by hand
(the router's ports, a warning's command), and the summary left in the terminal
lists it too. Going back is off while a task runs, and Ctrl+C asks for a second
press, because stopping half way can leave a half install.

:::caution
sslip.io is a shared domain: Let's Encrypt may refuse a certificate in a week
when too many were issued for it. A domain of your own, or DuckDNS, is more
reliable.
:::

If you ran the installer as your user instead of root, the Ports step also
asks *Allow them with one sudo command during the install?*, because a user
cannot bind 80 and 443 otherwise. Answer yes and, at the service row, the
screens step aside while `sudo` asks for your password once, then come back on
the same task.

Without a terminal, or with `--non-interactive`, setup prints plain lines and
takes every answer from flags, the environment and the existing file: see
[Command line](/telinha/reference/cli/#telinha-setup).

## Strict networks

Some viewers sit on networks that only let browsers reach port 443 (offices,
schools, some mobile carriers), where the media ports never get through. With
the address on 443, Telinha relays their video through `turn.<host>:443`,
which looks like any HTTPS site to those networks:
[TURN over TLS on port 443](/telinha/guides/turn/). The setup's Video step
asks *Also serve video through port 443 for strict networks?* (yes by default).
With a DuckDNS or sslip.io name that is all; with your own domain it first asks
you to add the DNS record `turn.<host>`, where `<host>` is the host of
`PUBLIC_URL` (for `https://telinha.example.com` that is
`turn.telinha.example.com`, see [DNS](/telinha/guides/turn/#dns)), pointing at
the VPS, and checks that it resolves. The `turn` row of doctor says whether it
works.

## Check it

```sh
sudo telinha doctor
```

Doctor is a checklist: one row per check, each with a spinner until it has its
result. Press Enter on a row to see its detail and, when it is not ok, the fix;
`r` runs every check again after you fix something. When the checks are done a
panel shows a link and a QR code for the phone test: open it on your phone with
Wi-Fi off, so the test runs over mobile data like many of your friends'
connections. It tells you whether the page, the LiveKit connection, UDP and TCP
all work from there, and with TURN on whether the video can relay through
`turn.<host>:443` (the TURN/TLS 443 row); `p` starts a new test; a first path to an IP that is
not the VPS's public IP means a wrong `LIVEKIT_NODE_IP`.
[Doctor and troubleshooting](/telinha/guides/doctor/) explains every row and
what a failure means.

## Use it

Type `/telinha` (or the command name you chose) in one of the channels you
picked. The bot posts a card with a button to a new room at
`https://<your address>/r/<code>`. Whoever opens it logs in with Discord once,
and members with the role get in. Share your screen from Chrome, Edge or
another Chromium browser; watching works on phones too. The card shows who is
streaming and who else is in the room, and the room closes by itself a few minutes
after everyone leaves.

## Day two

The service starts at boot, starts Telinha again after an update or a crash,
and logs to the journal:

```sh
sudo telinha service status
sudo telinha service restart
journalctl -u telinha -f
```

`systemctl` manages the `telinha` unit like any other; `telinha service start`,
`stop`, `restart` and `status` make the same calls.

**Updates** happen on their own: Telinha checks a few minutes after it starts
and then every few hours, waits while rooms are open, checks the sha256 and
rolls back a version that fails to start. `sudo telinha update --check` shows
where you stand and `sudo telinha update --now` installs at once. See
[Updates](/telinha/guides/updates/).

**Changing settings** means running `sudo telinha setup` again: every question
starts at the current value, secrets can be kept (Enter keeps them), and the service restarts with
the new file. Editing `/opt/telinha/config/telinha.env` by hand works too,
followed by `sudo telinha service restart`.

**Removing it**: `sudo telinha service uninstall` removes the unit and keeps
the files; then delete `/opt/telinha`.

[Running as a service](/telinha/guides/service/) has the details.
